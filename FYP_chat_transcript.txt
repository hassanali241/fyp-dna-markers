It means you need a comparison that separates two explanations for why the marker version might score better.

## The problem
Your marker version stores **less data** in each strand: 96 bases of your data instead of 128. The other 32 bases are markers the model already knows. So if it scores better, there are two possible reasons:

- **Reason A (what you hope):** the markers help the model work out where bases went missing. This is "synchronization".
- **Reason B (boring):** the model has less to recover. 96 unknown bases is an easier job than 128, and 32 of the bases are always the same, so they're easy to guess.

Your current design can't tell A from B.

## The fix: a third version (a "control")

| Version | What's in the 128 bases |
|---|---|
| 1. Marker-free | 128 data bases |
| 2. Periodic markers | 24 data + 8 marker, repeated 4 times |
| 3. **Control (new)** | 96 data bases, then all 32 marker bases bunched together at the end |

Versions 2 and 3 have the **same amount of data (96)** and the **same known bases (32)**. The only difference is that version 2 **spreads** the markers through the strand and version 3 **lumps** them at the end.

**Analogy:** you're reading a long sentence with some letters missing. Version 2 is like having a page number every few lines, so you can always check where you are. Version 3 puts all the page numbers on the last page, where they don't help you keep your place.

- If version 2 beats version 3, the spacing helps, so the markers really do help with synchronization (Reason A).
- If they score about the same, the improvement came from having less data to recover (Reason B), and the markers' spacing didn't matter.

## The two extra numbers
- **Per-base error rate:** the share of individual bases the model gets wrong. This is fairer than "whole strand perfect or not", because a 96-base strand is naturally more likely to come out perfect than a 128-base one.
- **Payload information rate:** how much of your data each strand carries. It's 128 out of 128 (100%) without markers and 96 out of 128 (75%) with them. Markers cost you 25% of your storage, so they need to improve accuracy by enough to justify that cost.

In your report, the claim would be: "markers help **because of where they are placed**, and the gain is worth the 25% storage cost." The control version is what lets you make the first half of that claim.

## What Stage 2 found in DNAFormer's own code
DNAFormer's data loader can't be used safely for your experiment:
- **It crashes on Colab.** It uses a Python feature that was removed in Python 3.11.
- **It throws away deletion-heavy reads.** At 8% deletion, only about 0.8 of each cluster's 10 reads would survive.
- **It silently swaps clusters.** When no reads survive, it replaces the cluster with a random other one. That would happen to **41% of your 8%-deletion test clusters**, so results would be measured on the wrong data.
- **It quietly blanks some reads.** A read that is exactly 132 bases long becomes all zeros.
- **Its weight loading never fails.** If the checkpoint doesn't match the model, the model just stays partly random instead of raising an error.

**The minimum safe fix**, which is what I built: a small adapter, [dnaf_adapter.py](fyp_dna/dnaf_adapter.py), that keeps all 10 reads and gives the **unchanged** DNAFormer exactly the input it expects (132 in, 128 out). It also refuses to continue if any pretrained weight fails to load. Later stages will reuse it.

## What a strand is
A **strand** is one short piece of DNA that holds your data, written with the letters A, C, G and T. Each strand here is **128 letters** long.

A **read** is a noisy copy of a strand, as a sequencing machine would give it back: some letters are missing, some are extra, some are wrong.

## How many
- **15,000 strands** in each version: 10,000 train, 1,000 validation, 4,000 test.
- **10 reads per strand**, so 150,000 reads per version.
- **3 versions** (no markers, periodic markers, end-block), so **450,000 reads in total**.

## How they're stored
There's one folder per version and split, for example `marker_periodic/test_del05/`. Each folder has three files:

**`clean.fasta`**: the original strands, one per entry.
```
>marker_periodic__test_del05_000000
TTGGACATTACGAGG...ACGTCAGT        (128 letters)
```

**`noisy_reads.fasta`**: the 10 reads for each strand, labelled read_0 to read_9.
```
>marker_periodic__test_del05_000000|read_0
TTGGACATTACGAGG...ACGTCAGT        (about 123 letters)
>marker_periodic__test_del05_000000|read_1
...
```

**`metadata.json`**: everything about each strand: its seed, deletion rate, marker positions, the data part on its own, and the reads.

There's also **`dataset_manifest.csv`**, a spreadsheet with one row per strand. You can open it in Excel or Google Sheets.
